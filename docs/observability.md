# 可观测性 Observability

> 本文是一个**横切关注点**的聚合视角，不新增实体。可观测性回答"用户如何看见一次调研全过程"，其依赖的实体（检查点、上下文快照、审计事件等）已在 `state.md` / `context.md` / `security.md` 中定义，本文只做统一命名与归口，不改设计真源。

---

## 1. 定位

研衡的护城河是「可验证的溯源 + 高信息密度产出」，其中"可审计"卖点就落在可观测性上。可观测性回答三问，对应业界三大支柱：

| 支柱 | 回答的问题 | 研衡承载实体 |
| --- | --- | --- |
| 追踪 Tracing | 结论是怎么来的 | 溯源链（证据台账 → 结论 → 报告） |
| 指标 Metrics | 过程健不健康 | 覆盖度、证据强度分布、重试次数、成本 / 延迟 |
| 审计 Audit | 每一步能不能复现 | 审计事件、检查点、上下文快照、人工干预记录 |

> 评估（Evaluation）是第四支柱，但研衡已单独拆成 `eval.md`，本文不涉及。可观测性回答"能不能看见"，评估回答"看见了好不好"。

---

## 2. 追踪 Tracing

追踪回答「一条结论的完整来源链」。每条关键结论应能追溯到四要素：

- **哪个 Agent**：产出角色（Lead / Collector / Verifier / Synthesizer）
- **什么上下文**：该角色当时的上下文快照（见 `context.md` §2）
- **哪个来源**：证据台账的引用（见 `state.md` §2.2 证据台账）
- **什么证据强度**：实锤 / 推断 / 共识 / 分歧

这条链是研衡「内联引用溯源」卖点的运行时体现，也是 `security.md` §2 边界三「可审计溯源」的具体落地。

---

## 3. 指标 Metrics

指标回答「过程健不健康」，从状态直接派生、可机器计算：

| 指标 | 来源实体 | 说明 |
| --- | --- | --- |
| 覆盖度 | 研究矩阵（`state.md` §2.2） | 0~1，格子状态派生，越低缺口越多 |
| 证据强度分布 | 结论 Claim 的证据强度 | 四档占比，实锤占比越高越可信 |
| 重试次数 | 子任务台账的重试次数 / 上限 | 逼近上限说明缺口难补 |
| 成本 / 延迟 | 审计事件的耗时与 token | 来自审计事件载荷（见 `security.md` §3） |

---

## 4. 审计 Audit

审计回答「每一步能不能复现」，依赖四类实体，统一在**同一审计语义**下对齐：

- **审计事件**：事件类型（上下文编译 / 状态写入 / 工具调用 / Skill 加载 / 派发 / 注入扫描 / 隐私脱敏）、主体、已脱敏载荷、溯源链、时间（见 `security.md` §3）
- **检查点**：super-step 状态快照，支持断点确定性续跑（见 `state.md` §2.2）
- **上下文快照**：每次编译记录"该角色看到了什么"，用于溯源判断依据（见 `context.md` §2）
- **人工干预记录**：谁在哪个检查点做了什么决策（见 `state.md` §2.2）

四者对齐，保证「任何一个判断都能追溯到当时的状态、上下文、来源与决策」。

---

## 5. 与各模块的映射

可观测性不持有实体，只归口引用：

| 支柱 | 主要承载模块 | 文档 |
| --- | --- | --- |
| 追踪 | State（溯源链）+ Context（快照） | `state.md`、`context.md` |
| 指标 | State（覆盖度 / 证据强度） | `state.md` |
| 审计 | Security（审计事件）+ State（检查点 / 干预记录）+ Context（快照） | `security.md`、`state.md`、`context.md` |

---

## 6. 与 eval.md 的边界

- `observability.md`：**能不能看见**——追踪链、指标、审计日志是否齐全、可复现。
- `eval.md`：**看见了好不好**——报告质量、事实引用、过程质量的三层评分。

两者互补：先有可观测性（有数据可看），再有评估（对看到的数据打分）。

---

## 7. 生产级落地规范

### 7.1 指标名（供 `operations.md` 采集）

| 指标名 | 类型 | 说明 |
|---|---|---|
| `research_coverage` | gauge | 覆盖度 0~1 |
| `research_unresolved_ratio` | gauge | unresolved 子任务占比 |
| `llm_latency_p95` | histogram | LLM 调用时延 p95 |
| `llm_retry_ratio` | gauge | 重试占比 |
| `token_consumed_total` | counter | token 累计消耗 |

### 7.2 日志字段规范

统一结构化字段：`timestamp` / `level` / `run_id` / `thread_id` / `event` / `payload`（见 `operations.md` §5）。

### 7.3 trace 传播

`run_id` + `thread_id` 贯穿全链路：HTTP 头 → 图执行 → LLM / 工具调用 → 审计事件，保证任意一步都能关联回所属调研任务。
