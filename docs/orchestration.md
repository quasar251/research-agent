# 调度 Orchestration

> 本文对应《核心设计》`agent-core.md` 的 §5 调度模块，并承接第二档功能 ④⑤⑥ 的调度侧。
> Orchestration 是状态图上的**节点派发**：由 Supervisor 按「阶段 + 依赖」派发子任务、聚合结果、重派缺口。

---

## 1. 职责

Supervisor + **阶段感知 + 依赖感知**，而非关键词路由，也非无差别并行 fan-out。阶段映射见 `state.md` §1.2。

关键定位：Supervisor 是调度器组件，**不是 Agent 角色**——它不产出结论，只负责「谁在何时做什么」。

---

## 2. 调度的组织方式

- **调度计划**：运行标识、阶段序列、预期产出表、派发单元列表。
- **派发单元**：子任务 id、指派角色、依赖、预期产出。
- **聚合结果**：预期产出 vs 实际落地，输出缺口单元（重派）、unresolved 清单（重试上限后显式标记）。

---

## 3. 与其他模块的耦合

- **读 / 写状态**：派发即状态图上的节点派发；子 Agent 作为 "agent-as-tools" 被调用。
- **聚合**：合成 Agent 读取所有子任务结论做去重，输出带显式 unresolved 章节的结果。

---

## 4. 缺口重派与 unresolved（④ 迭代式缺口填补）

第二档功能 ④，是 Orchestration 与 State 覆盖度指标的组合：

1. 覆盖度由研究矩阵格子状态派生、写时重算（见 `state.md` §2.2）。
2. Supervisor 对比「预期产出」与「实际落地」，识别缺口单元。
3. 只重派缺口，不重跑已完成部分；重试达到上限后用 unresolved 显式标记。
4. **绝不静默跳过**：缺口要么被重派，要么显式 unresolved。

---

## 5. HITL 审批点（⑤ 前置澄清）

第二档功能 ⑤，在 align 阶段前置人工澄清：

- 注入点：align 阶段，澄清口径 + 确认研究矩阵。
- 人工干预记录写入状态（检查点、操作者、决策内容、时间），可审计。
- 审批结果分「通过继续」与「打回重写」，打回则重新执行当前阶段。

---

## 6. 事件触发（⑥ 持续监测的调度侧）

第二档功能 ⑥，跨会话复用长期记忆（记忆侧见 `memory.md`），调度侧负责事件触发短简报：

- 触发点：新任务 align 阶段读取已沉淀的长期记忆。
- 产出：基于既有记忆生成的短简报，作为新任务的上下文注入。

---

## 7. 关键设计点

- **对比预期与落地**：只重派缺口，重试上限后用 unresolved 显式标记。
- **聚合不用简单拼接**：核查 Agent 做证据分级与交叉验证（证据侧），合成 Agent 做结论去重与一致性校验（结论侧）。
- **阶段感知 + 依赖感知**：先对齐、再搜集、后缺口；依赖未满足的子任务不提前派发。

---

## 8. 生产级关注点

### 8.1 缺口重派循环条件

- verify 后判断：**覆盖度 < 目标阈值（默认 0.9）且存在 gap 且未超重试上限** → 回 collect 重派缺口。
- 重试超限 → 显式标 unresolved，不再重派（幂等，见 `reliability.md` §4）。

### 8.2 并发与背压

- fan-out 并发上限（默认 4 路），超出排队。
- 背压：LLM 限流（429）时暂停派发，指数退避后恢复（见 `reliability.md` §2）。

### 8.3 幂等

- 派发单元以子任务 id 幂等，重派用 `_upsert_by_id` 合并，不重复创建条目。
- 静默缺口禁止：缺口必须重派或标 unresolved，见 `reliability.md` §1。
