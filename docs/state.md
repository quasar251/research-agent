# 状态 State 与全局约定

> 本文对应《核心设计》`agent-core.md` 的 §3 全局约定 + §4 状态模块。
> State 是「**单一事实源**」：当前调研任务的运行时图状态。全局约定是所有模块共享的公共坐标系，在此一并定义。

---

## 一、全局约定

### 1.1 角色集合

四个 Agent 角色，贯穿上下文编译、调度派发与审计溯源：

| 角色 | 职责 | 校验边界 |
| --- | --- | --- |
| Lead | 规划者：生成研究矩阵、拆解子任务、监控进度、发起缺口补充 | 管"查什么、查全没" |
| 搜集（Collector） | 执行者：按子问题采集信息、抽取结构化结论、更新证据台账 | 管"有没有、哪来的" |
| 核查（Verifier） | 证据侧：对来源 / 证据做可信度分级与交叉验证，给结论标注证据强度 | 管"证据可不可信" |
| 合成（Synthesizer） | 结论侧：聚合结论、去重、产出报告，不重复做证据分级 | 管"结论矛不矛盾" |

**Supervisor 定位**：Supervisor 属 Orchestration 模块的调度器组件（见 `orchestration.md`），不是第五个 Agent 角色——它不产出结论，只负责按阶段派发子任务、对比预期与实际产出、重派缺口。与 Lead 的分工：Lead 管"查什么、查全没"，Supervisor 管"谁在何时做什么"。

**演示层别名**：演示层 Mock（`frontend/`）为便于可视化，使用 `Master / Scout / Analyst / Critic` 四个节点别名：

| 后端角色 | 演示层别名 |
| --- | --- |
| Lead | Master（规划 / 主笔） |
| Collector（搜集） | Scout（检索） |
| Verifier（核查） | Critic（审查） |
| Synthesizer（合成） | Master（整合报告）+ Analyst（结构化分析） |

### 1.2 阶段集合

阶段是调度与 Skill 路由的公共坐标系，四阶段即可：

| Stage | 含义 |
| --- | --- |
| align | 前置对齐：澄清口径 + 确认研究矩阵（含 HITL 澄清） |
| collect | 并行搜集（fan-out） |
| verify | 缺口补充 + 交叉核查（循环，直到覆盖度达标或标 unresolved） |
| synthesize | 合成报告 |

**与演示层的阶段映射**：演示层 Mock 的深度调研为五阶段（四阶段的可视化展开），简单调研为三阶段轻量管线（无审批，是收敛子集）。

| 后端阶段 | 演示层深度阶段 | 说明 |
| --- | --- | --- |
| align | 任务拆解 | 澄清口径 + 确认研究矩阵 |
| collect | 数据检索 + 深度分析 | 采集与结构化结论抽取 |
| verify | 交叉审查 | 缺口补充 + 交叉核查 |
| synthesize | 生成报告 | 聚合去重 + 成稿 |

### 1.3 引用语义

- 所有台账实体（子任务、证据、结论、检查点等）用**全局唯一 id** 标识。
- 跨实体引用一律用 id（引用字段），**不内联对象**，保证状态是单一事实源、无冗余副本。

### 1.4 报告结构 schema

报告是调研任务的最终交付物，由合成角色产出，章节结构为固定骨架（两档共用，deep 全量、simple 收敛）：

| 区块 | simple | deep |
| --- | --- | --- |
| 执行摘要（核心指标 + 摘要） | 简 | 全 |
| 核心结论 KEY TAKEAWAYS（证据强度 + 引用） | 简 | 全 |
| 行业定义与宏观环境（PEST） | 简 | 全 |
| 市场规模（CAGR、供需） | 简 | 全 |
| 产业链图谱（上中下游、价值分布） | — | 全 |
| 竞争格局（头部份额、波特五力） | 简 | 全 |
| 趋势研判（演进方向） | — | 全 |
| 风险提示（关键风险） | 简 | 全 |
| SWOT 分析（四象限） | — | 全 |
| 结论与建议（评级 + 可执行建议） | 简 | 全 |
| 信息来源 References（证据强度） | 简 | 全 |

- 该结构是 Skill 的组成部分（见 `skill-design.md`），也是用户偏好可调整的维度。
- 简单模式收敛的章节以「简」标注；产业链、趋势研判、SWOT 为深度专属，简单模式不展开。

## 二、状态 State

### 2.1 职责

存的是**图状态**，不是对话历史。行业调研是多步、长时、可中断的流程，采用"有状态图 + 检查点"：

- 每个节点接收状态、返回**状态更新**（reducer 合并）。
- 每个 super-step 边界自动持久化状态快照，支持断点确定性续跑（而非随机重新生成）。

### 2.2 状态包含的实体

**研究矩阵**：当前任务的填充进度。"公司清单 × 维度清单"构成格子矩阵，每个格子记录：

| 字段 | 说明 |
| --- | --- |
| 公司 / 维度 | 格子坐标 |
| 状态 | covered（已覆盖）/ gap（缺口）/ unresolved（无法解决） |
| 证据引用 | 指向证据台账，保证"结论可归因" |
| 结论引用 | 指向结论台账 |
| 摘要 | 该格子的结论摘要 |

矩阵整体带**覆盖度**指标（0~1），由格子状态派生、写时重算，驱动"缺口填补"。

**子任务台账**：每个子任务的执行状态。

| 字段 | 说明 |
| --- | --- |
| 唯一 id / 问题描述 | 标识与任务内容 |
| 指派角色 | 由哪个 Agent 执行 |
| 执行状态 | pending / running / completed / unresolved |
| 所属阶段 | 见 §1.2 |
| 依赖 | 前置子任务 id 列表，调度做依赖感知 |
| 重试次数 / 上限 | 控制缺口重派 |
| 产出引用 | 指向结论台账 |

**证据台账**：已采集来源的登记。

| 字段 | 说明 |
| --- | --- |
| 唯一 id / URL / 抓取时间 | 来源标识 |
| 可信度评分 | 0~1 |
| 来源等级 | 1 / 2 / 3 三级治理 |

**结论台账（Claim）**：子 Agent 的产出，是"带证据的结论"的统一表示。

| 字段 | 说明 |
| --- | --- |
| 唯一 id / 结论内容 | 产出内容 |
| 证据强度 | 实锤 / 推断 / 共识 / 分歧 |
| 证据引用 | 指向证据台账 |
| 产出角色 / 时间 | 溯源 |
| 状态 | 草稿 / 已验证 / 已沉淀（沉淀逻辑见 `memory.md`） |

> 裁剪说明：原设计把"记忆层事实"与"状态层发现"拆成两套结构，实为同一实体的两个生命周期，已统一为**结论（Claim）**一种结构。

**人工干预记录**：谁在哪个检查点做了什么决策（检查点、操作者、决策内容、时间）。

**检查点**：super-step 的状态快照（唯一 id、状态快照、时间、前驱检查点），用于断点续跑。

**根状态**：把以上全部组织起来，含运行标识、用户标识、调研意图、当前阶段、检查点链。

### 2.3 与其他模块的耦合

- **供调度派发**：Supervisor 读子任务状态、写状态更新（见 `orchestration.md`）。
- **供上下文编译**：Context Compiler 只读状态，生成各角色视图（见 `context.md`）。
- **供记忆投影**：任务收尾时，蒸馏节点把"验证有效"的结论沉淀进长期记忆（见 `memory.md`）。
- **供安全横切**：所有状态写入审计日志前，先过隐私脱敏（见 `security.md`）。

### 2.4 关键设计点

- **检查点**：第 30 步崩溃，从第 30 步恢复，保证确定性续跑。
- **静默缺口是最危险的状态**：缺口要么被重派，要么显式标记 unresolved，绝不静默跳过。
